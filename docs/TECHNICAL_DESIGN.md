# 商证 MerchantLens｜技术设计与模型边界

版本：作品集原型 v1 · 2026-10-03

## 1. 系统架构

```text
浏览器：TypeScript / Vite
  ├─ 商户与账单日选择、对账面板、异常明细
  ├─ 请求解释、证据展示、工单草稿、评测与资料
  └─ 默认本地证据路径
       ├─ Scope 校验 → 合成账单范围过滤
       ├─ 整数分对账与异常规则
       ├─ 中文片段分词 + BM25 风格规则召回
       └─ 引用证据的确定性说明

可选 Node 服务端模型路径
  ├─ GET /api/model-status：配置状态
  └─ POST /api/assist：query + scope
       ├─ 重新取得允许范围的合成证据
       ├─ 构建受约束提示与来源白名单
       ├─ TokenHub / 混元兼容 Chat Completions
       ├─ 结构与 citations 校验
       └─ 有效解释 / 明示失败 → 本地证据回退
```

本轮没有数据库、登录体系或真实支付连接。合成数据隔离是输入范围控制的演示；前端选择器不是生产权限系统。生产化时应将身份、商户授权、数据读取与金额计算放在服务端，以已登录身份取得租户范围，而非信任用户传入 `merchantId`。

## 2. 数据模型

| 对象             | 关键字段                                          | 设计意义                     |
| ---------------- | ------------------------------------------------- | ---------------------------- |
| Scope            | `merchantId`、`billDate`                          | 每个答案有唯一的数据范围     |
| Trade            | `id`、商户、日期、金额分、手续费分、SUCCESS       | 支付记录，作为核对证据       |
| PosOrder         | `id`、商户、日期、金额分                          | 商户侧订单                   |
| Refund           | 退款 ID、原订单 ID、商户、日期、金额分、状态      | 退款记录，状态与金额不能混淆 |
| Finding          | 类别、金额、严重度、订单 ID、说明                 | 将“有差额”分解为可处理异常   |
| KnowledgeChunk   | ID、标题、文本、URL、authority、更新时间、tags    | 规则来源区分官方与演示       |
| Evidence         | ID、ledger / knowledge / calculation、详情、URL   | 回答与工单的可核查依据       |
| Answer           | intent、status、sections、evidence、steps、engine | 将回答、拒答与澄清显式建模   |
| EvaluationResult | 场景 ID、分组、各检查结果、输出答案               | 允许失败追溯到具体场景       |

合成数据仅覆盖 3 个商户与 2026-09-28 / 29；这些日期是样例数据的标签，不表示真实经营数据。演示费率属于自定义合成合同条件，不能向用户解释为微信支付统一官方收费标准。

## 3. 计算与对账

金额变量以整数分表示，整数安全范围必须可校验。真实 CSV 导入应将元字符串转为整数分，拒绝非法精度、空值、非数字或溢出；展示时再格式化为元。

首版核对次序：范围过滤 → 订单索引 → POS 重复识别 → 支付 / POS 单边缺失 → 同订单金额核对 → 演示手续费校验 → 退款状态核查 → 汇总。差额定义为 POS 导入总额 − 支付导入总额，汇总保留重复 POS，解释与异常证据单独揭示重复影响，不自动改账。生产接入还需增加记录完整性检查与支付侧重复检测。

简化账面净额：`成功支付交易总额 − 当日 SUCCESS 退款 − 账单列示手续费`。这只是演示分析值，未纳入资金账单、手续费退回、账期、银行流水和资金冻结等因素。**PROCESSING 不计为成功退款，并不意味着退款受理后资金尚未扣除。**官方退款流程说明受理后资金可能进入退款中间账户，最终状态需要查询或通知确认。[微信支付：退款开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)

## 4. 默认证据与检索路径

小规模规则库采用中文字符片段与英文词项形成 token，使用 BM25 风格的词项权重、词频与长度归一化排序，再按问题意图组织规则。该方案的优点是无需密钥、可复验、易看来源；局限是不能等同语义理解，口语改写与隐含意图需要补充样例和标注。

召回只用于选择知识片段，不决定交易金额。规则片段保留 authority、URL 与版本日期；`demo` 规则不能包装成官方规则。未命中、规则冲突、范围不明确时，应澄清或说明证据不足，不能以检索分数产生未经校准的“准确率”或“置信度”。

“引用”也需要分两层核查：链接存在只证明来源可打开；内容是否支持当前结论，必须按语义和适用条件核验。

## 5. 模型服务契约

### 配置

- `TOKENHUB_API_KEY`：优先使用的新平台密钥。
- `HUNYUAN_API_KEY`：兼容备用密钥入口，不保证不同平台密钥互通。
- `MODEL_BASE_URL`：默认 `https://tokenhub.tencentmaas.com/v1`；选择新加坡站点时需使用该站点密钥。
- `MODEL_NAME`：必须显式配置已开通模型，例如官方当前列表中的 `hy3`；可用模型会变化，接入时重新核验。

密钥只放服务端环境变量，不放 `VITE_*`、源码、下载文件或浏览器请求负载。API 兼容不等于账号已开通，也不等于调用成功。TokenHub 官方文档指出站点密钥与模型开通状态会影响调用。[腾讯云：语言模型调用概览](https://cloud.tencent.com/document/product/1823/130079)

### 接口

`GET /api/model-status` 返回 `{ configured, available, provider, model, mode }`。`configured` 表示本地配置校验通过；`available` 初始为 false，只有一次有效模型请求完成后才置为 true，之后调用失败则回到 false。该状态不是持续远程健康检查；配置存在也不等于模型已调用成功。

`POST /api/assist` 接收 `{ query, scope }`，有效响应为 `{ text, model, citations }`。服务端按 scope 重建允许范围证据，避免客户端提供一个被篡改的金额结果后要求模型解释。

模型调用使用 `/chat/completions` 路径，非流式、温度 0.1、输出预算 1,200 tokens，总超时预算为 25 秒；仅在 HTTP 429 / 503 时最多重试一次。结构错误、JSON 不可解析、引用不在白名单等输出会被拒绝。客户端显式显示失败 / 回退状态，不把确定性回退包装为混元回答。

旧混元平台文档已提示相关功能逐步迁移至 TokenHub，新服务接入应优先核对新平台指南。[腾讯云：原平台迁移提示](https://cloud.tencent.com/document/product/1729/111007)

## 6. 模型职责与校验层

模型允许：将结构化异常解释为易懂语言；总结证据；生成不含资金动作的工单措辞；识别需要补充的信息。

模型禁止：自行计算或改变金额；跨商户检索；推断缺失交易；承诺到账时间；输出真实账户敏感信息；直接创建退款、转账或账务调整。

服务端将 query 视为用户输入，而不是系统指令。账单备注、文档内容也都视为数据。模型只能使用白名单来源与已计算证据；金额展示仍以确定性结果为准，模型文字不能覆盖账单卡片。输出校验能降低风险，但只校验 JSON 和引用 ID 不能证明语义完全正确。真实模型上线前还需检查数字、状态、范围、归因和下一步是否与证据一致，并加入对抗样例。

工具与证据轨迹展示的是可审计的业务步骤，不是模型内部思维链。用户需要知道查了什么和依据是什么，无需看到未经验证的长推理文本。

## 7. 安全与生产差距

| 风险       | 演示设计                              | 生产化要求                                      |
| ---------- | ------------------------------------- | ----------------------------------------------- |
| 跨商户访问 | 校验允许商户与当前范围、拒绝越界查询  | 服务端身份 → 授权租户映射；数据层隔离；对抗测试 |
| 提示注入   | 将用户 / 规则文本当数据，保留固定职责 | 输入分层、工具权限、输出语义校验、攻击回归      |
| 金额幻觉   | 整数计算证据、前端金额不被模型覆盖    | 服务端复算、账单字段校验、差错告警              |
| 资金误操作 | 不提供退款 / 转账执行工具             | 独立审批、幂等、操作审计和业务赔付机制          |
| 密钥泄露   | 服务端环境变量                        | 密钥管理服务、轮换、访问控制、脱敏日志          |
| 数据泄露   | 只用合成记录                          | 数据最小化、地域与保留期限、授权和删除机制      |
| 模型不可用 | 25 秒超时和证据路径回退               | 监控、限流、熔断、成本预算、回滚开关            |

## 8. 可复验评测

报告位置：`public/artifacts/evaluation-report.json` 与 `public/artifacts/evaluation-report.md`。页面与材料应从实际执行报告读取，不手填通过率。

测试至少拆开金额计算、异常识别、请求意图、证据引用、范围约束、拒答 / 澄清与模型接口行为。真实模型评测要披露模型名、执行日期、提示版本、温度等关键配置、分组样本与失败案例；不能将本地模板测试当作真实 LLM 测试。

本地场景结果不证明 production readiness。特别是 3 个商户、2 个日期的隔离回归只能验证演示约束，不能证明 IAM、数据库行权限或云环境权限已完成。

## 9. 可观察性与审计建议

生产日志建议记录：请求 ID、脱敏用户 / 租户标识、账单范围、规则版本、数据校验状态、命中证据 ID、模型版本、耗时、token 与成本、拒答原因、人工修订和最终处理结果。默认不记录完整消费者身份、API 密钥或模型内部思维链。

把“模型失败”和“业务异常”分别统计：一个是服务质量，一个是客户需要处理的任务。回滚时保留确定性证据与原始工单，不因模型关闭而丢失处理中异常。
