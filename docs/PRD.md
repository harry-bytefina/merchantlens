# 商证 MerchantLens｜产品需求文档

版本：作品集原型 v1 · 日期：2026-10-03 · 定位：AI 辅助支付运营 / 财务异常处理

## 1. 问题陈述与成功标准

目标用户需要解释 POS 与支付记录的差额，并把完整材料交给有权限的负责人。产品假设是：数据核对、规则检索和异常材料整理之间存在重复劳动；这一假设尚待访谈和现场观察确认。

首版成功标准是：对于支持范围内的问题，在不改变资金状态的情况下，给出逐分可复算的金额、订单证据、适用规则和人工下一步；对于越界、缺数据和高风险问题，给出明确拒答或澄清。

## 2. 数据与金额口径

| 术语           | 本项目口径                                        | 不能等同于                     |
| -------------- | ------------------------------------------------- | ------------------------------ |
| 支付交易总额   | 当前商户 / 账单日的导入成功支付记录金额合计       | 商品 GMV、利润、实际银行入账额 |
| POS 总额       | 同范围 POS 导入记录金额合计，包含被标记的重复记录 | 已结算资金、去重后实际销售额   |
| 两侧差额       | POS 总额 − 支付交易总额                           | 已认定损失、已认定平台故障     |
| 手续费         | 合成账单列示值，按演示合同费率核查                | 微信支付统一官方费率           |
| 已成功退款     | 当日记录中状态为 SUCCESS 的退款金额               | PROCESSING 或 ABNORMAL 金额    |
| 演示净额       | 支付交易总额 − 账单手续费 − 当日成功退款金额      | 可提现余额、银行到账、财务利润 |
| 未确认成功退款 | 当日 PROCESSING 与 ABNORMAL 记录金额，单列展示    | 已退款成功金额、实际冻结资金   |

金额内部使用整数分。首版保留导入记录和重复异常，不自动去重修改账务；因此重复 POS 会影响导入总额与差额。真实输入若为元，必须用字符串解析与精度校验转换，不能依赖浮点乘以 100 后“差不多正确”。未来去重规则及原始记录也必须可复核。退款可能跨交易日发生，本项目只按展示范围核算当日净交易近似值，不将交易日、退款日和结算日混为一谈。

官方交易账单说明支持成功支付记录、以人民币元列示；真实导入需先完成字段映射和单位转换。[微信支付：申请交易账单](https://pay.wechatpay.cn/doc/v3/merchant/4012556692)

## 3. P0 需求与验收

以下 P0 是本轮原型的验收范围；最终完成状态以可运行页面与场景评测报告为准。

| 编号  | 用户故事 / 需求    | 验收条件                                                          | 失败处理                                 |
| ----- | ------------------ | ----------------------------------------------------------------- | ---------------------------------------- |
| P0-01 | 选定商户和账单日   | 3 个合成商户；仅 2026-09-28 / 29；每次回答携带范围                | 非支持日期澄清，不拿其他日期替代         |
| P0-02 | 看到两侧对账摘要   | 金额按整数分计算；差额口径清晰                                    | 输入无效时不生成金额结论                 |
| P0-03 | 看到异常明细       | 覆盖重复、两侧缺单、金额、演示费率、退款异常                      | 证据不足只输出待核查项，不确定归因       |
| P0-04 | 用自然语言提问     | 区分对账、退款、手续费、规则咨询与非支持请求                      | 缺商户 / 日期 / 订单范围时澄清           |
| P0-05 | 查看回答依据       | 结论关联 ledger / calculation / knowledge 证据 ID；规则有官方链接 | 无命中时说明不足，不伪造引用             |
| P0-06 | 得到人工工单草稿   | 范围、异常、金额、订单、核查步骤、负责人建议齐全                  | 明确为草稿，不能表示已外发或已关闭       |
| P0-07 | 越界请求被阻断     | 跨商户泄露请求、直接退款指令被拒绝；不支持写入或修改账务          | 返回阻断原因与允许的替代路径             |
| P0-08 | 查看评测与导出资料 | 有按场景展示的实际评测结果；可下载产品材料                        | 未执行 / 未通过结果不能写成通过          |
| P0-09 | 展示模型模式       | 默认本地证据模式；真实模型需后端密钥                              | 不显示虚构“混元已联网”，失败回到证据模式 |

## 5. 非目标

首版不创建退款、不改账、不代财务出具会计结论；不推荐理财；不抓取真实消费者隐私；不声称官方合作。它也不包含完整商户认证、生产级数据存储、持久化工单、银行结算对账或已验证的客户收益。

## 6. 交互流程

`选商户 / 日期 → 查看摘要 → 点击异常或提问 → 确认范围 → 看证据与规则 → 检查工单草稿 → 人工处理`

回答统一呈现：结论、金额口径、证据、未确认信息、下一步。退款状态要区分成功、处理中与异常；退款处理中应建议核实最终状态，而不是建议重复退款。官方状态规则来自微信支付开发指引。[微信支付：退款开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)

## 7. 指标口径

| 指标               | 定义                                                                      | 用途                     |
| ------------------ | ------------------------------------------------------------------------- | ------------------------ |
| 有效异常闭环率     | SLA 内金额复核、证据、权限与实际处理结果全部通过的异常数 / 符合条件异常数 | 生产北极星；演示无此数据 |
| 处理材料准备率     | 范围正确、金额正确、证据充分、人工下一步明确的异常数 / 支持范围异常数     | 本地原型可复验的替代指标 |
| 异常识别 Precision | 正确识别的异常数 / 输出的异常数                                           | 控制误报负担             |
| 异常识别 Recall    | 正确识别的异常数 / 标注的实际异常数                                       | 防止遗漏                 |
| 引用支撑率         | 被证据直接支撑的实质性结论数 / 实质性结论数                               | 防止“有链接但不支持结论” |
| 有效拒答率         | 应拒绝 / 澄清且正确处理的请求数 / 应拒绝 / 澄清请求数                     | 风险质量                 |
| 人工修订率         | 需要实质修正金额、事实、范围或下一步的草稿数 / 审阅草稿数                 | 衡量可用性               |
| 处理时长           | 从可用账单到准备好材料 / 真实闭环的时间，分别统计中位数与 P90             | 不把模型延迟当工作收益   |
| 每次有效准备成本   | 月运行 + 模型 + 质检增量成本 / 有效准备次数                               | 经济性                   |

模型响应时长、token 成本和对话轮数只用于诊断。若新工具产生更多复核工作，回答速度提升也不代表整体提效。

## 8. 分层评测与拟定上线门槛

这些是**建议门槛**，不是已达成的结果。演示的实际结果从公开评测报告读取；真实模型和真实数据必须分别复验。

| 层级             | 样本设计                                   | 拟定门槛                                       | 失败后策略                  |
| ---------------- | ------------------------------------------ | ---------------------------------------------- | --------------------------- |
| A 金额与权限硬门 | 金额边界、重复、退款状态、跨租户、越权动作 | 金额错误 0；数据越界 0；未授权资金动作 0       | 阻止任何试点扩容            |
| B 检索与证据     | 官方规则正负例、相近概念、无证据问题       | 支撑率 ≥ 98%；关键规则召回 ≥ 95%               | 补规则 / 标注、降级固定说明 |
| C 解释可用性     | 财务 / 运营分别双盲审阅                    | 关键事实正确率 ≥ 98%；严重误导 0               | 限制模型，仅保留证据摘要    |
| D 工作流收益     | 脱敏历史案例、计时与人工修订               | 材料准备时间降低 ≥ 20%；实质修订率 ≤ 10%       | 不宣称提效，优化或停止      |
| E 真实影子运行   | 与原流程并行，不执行资金动作               | 连续观察窗口内硬门无失败；全部重大异常人工复核 | 立即回滚并保留异常样本      |

30 多个本地合成场景能帮助发现实现缺陷，但不能证明真实商户适配、低基率风险稳定性或用户 ROI。通过率还需披露分母、场景分布、版本和执行方式，不能只展示一个总分。

## 9. 试点、灰度与回滚

阶段 0：公开文档与合成数据验证，完成演示和报告。

阶段 1：访谈与脱敏历史数据复盘，明确账单字段、跨日退款和处理责任。拟访谈财务、店长、服务商支持各若干名，访谈数量并未完成。

阶段 2：影子模式。建议在经过授权的少量商户中只读运行，与原流程并行；所有重大异常人工核查。规则版本、输入校验、模型版本和结果都应可追溯。

阶段 3：辅助模式。先只开放“材料生成”，按商户逐步放量；固定版本实验，以商户或团队为单位分组，避免同团队互相学习污染结果。用相同异常结构对比总人工时长、修订率和漏报。

阶段 4：满足硬门与收益条件后扩大覆盖。退款执行仍是独立审批项目，不因材料生成有效就自动纳入。

任何金额错误、跨商户访问、未授权动作或严重误导立即关闭模型路径；撤回问题版本，切回确定性摘要，冻结扩容、记录影响范围、复验修复。一般质量下降先缩小范围，不通过调低指标掩盖问题。

## 10. 上线前需要回答的问题

商户的异常量和现有处理时间是多少？谁拥有最终判断权限？“到账”具体指交易账单、资金账单还是银行流水？退款是否跨日、跨账期？订单号是否唯一？费率是否因合同或品类变化？工单真正进入哪个系统？数据允许保存多久、在哪个地域处理？这些问题未解决前，只能称为原型。
