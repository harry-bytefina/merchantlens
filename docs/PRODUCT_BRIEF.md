# 商证 MerchantLens｜微信支付商户对账与异常处理 Copilot

> 腾讯 CDG—金融科技 AI 产品经理求职作品集 · 独立场景研究、可复验原型与模拟实习训练 · 2026-10-03
>
> 本项目根据公开文档设计，使用合成商户与账单数据。它不是腾讯内部项目，也未连接真实商户、支付账户或生产业务。默认演示由本地证据与规则引擎运行；模型接入代码与真实模型调用分别标注。新增训练材料覆盖选型、数据口径、异常归因、AI 架构、跨部门评审与灰度决策；交互训练功能与用户练习完成状态以实际验收 / 提交记录为准，不将模拟训练写成真实实习。

## 1. 一句话产品定义

把商户的“账单对不上，接下来怎么办”，转化为一条可复核的工作链：**核对账单 → 定位异常 → 出示交易证据 → 检索官方规则 → 解释下一步 → 人工处理工单**。

目标不是让模型替财务做决定，而是缩短财务从发现差异到准备好处理材料的距离。金额由确定性程序计算，模型仅承担语言理解、摘要和解释；是否发起退款、是否调整账务、是否关闭异常始终由有权限的人决定。

作品同时作为一段“线上实习训练”：学习者沿六项任务扮演 PM，读业务材料、做取舍、写交付物、根据 rubric 修订，从使用产品进一步过渡到解释产品。公开业务地图见 BUSINESS_MAP，任务输入、交付与验收见 INTERNSHIP_CURRICULUM。训练角色与来信是设计情境，不是腾讯内部流程记录。

## 2. 为什么选择这个场景

候选人具备金融工程、数据分析和金融科技相关经历。对账场景能够把这些背景转化为 AI 产品能力的可见证据：能否定义金额口径，能否找到业务风险，能否安排系统与人的职责，能否设计评测和收益验证。

微信支付官方提供交易账单下载和退款状态查询相关开发文档，因此问题可以落到明确的字段与规则上，而非仅做聊天演示。[微信支付：下载账单开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071218)、[微信支付：退款开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)

以下痛点是**产品假设**，尚未通过商户访谈验证：多店商户可能需要在 POS、支付账单、退款记录与内部协作工具之间反复切换；异常说明可能缺少订单证据；退款处理中可能被误解为退款成功；服务商运营人员可能将“支付侧有差异”直接归因为平台故障。产品先验证这些工作障碍是否存在，以及解释和工单材料是否真的能节省时间。

## 3. 首批用户与 JTBD

| 角色            | 要完成的工作               | 当前可能的障碍（待验证）             | 产品交付物                             |
| --------------- | -------------------------- | ------------------------------------ | -------------------------------------- |
| 多店商户财务    | 解释某商户某账单日的差额   | 金额口径不一致、记录重复、两侧缺单   | 明确口径的账单摘要、异常明细与订单证据 |
| 商户运营 / 店长 | 将问题转给合适的负责人     | 无法区分退款状态、账单延迟和真实差额 | 附证据和下一步核查项的工单草稿         |
| 服务商支持人员  | 复现问题，减少反复索要信息 | 商户描述模糊、数据范围不清楚         | 商户范围、账单日、异常类别、引用规则   |

核心 JTBD：**当次日核对到账相关记录时，我希望知道差额来自哪些订单、哪些规则适用，以及应交给谁核查，以便在不误操作资金的前提下完成异常处理。**

## 4. 最小闭环与演示边界

1. 选择合成商户与账单日。演示仅有 3 个商户、2026-09-28 / 2026-09-29 两个日期。
2. 程序以整数分核对 POS 与支付记录，展示重复、缺单、金额差异、演示费率异常和退款状态。
3. 用户提出问题；引擎识别请求范围，检索带来源的规则片段，返回计算证据和下一步。
4. 生成工单草稿，由人检查、复制或导出。草稿不等于已处理，不等于已经退款。
5. 在评测页面查看场景级结果，再阅读产品、技术与面试材料。

本地演示展示的是“准备处理材料”的闭环。生产闭环还需要身份鉴权、真实账单接入、审批、责任人响应、结果核验和关闭记录。这些不能凭前端下拉选择或一段 AI 回答替代。

## 5. AI 与确定性系统的分工

| 工作                           | 执行者                       | 原因                             |
| ------------------------------ | ---------------------------- | -------------------------------- |
| 金额转换、汇总、差额、重复检查 | 确定性程序                   | 需要逐分准确、可复算             |
| 商户 / 日期约束、越界阻断      | 规则与服务端权限机制         | 模型判断不能成为权限边界         |
| 官方规则召回                   | 本地检索；后续可升级检索服务 | 能展示来源、版本与适用条件       |
| 异常解释、摘要、工单措辞       | 当前模板；可选混元           | 适合语言任务，必须依赖已计算证据 |
| 发起退款、调整账务、关闭工单   | 有权限的人与受控业务系统     | 涉及真实资金和业务责任           |

默认版本采用 BM25 风格的词项排序和中文字符片段检索，不使用向量数据库，也不宣称已完成生产级 RAG。腾讯 TokenHub 提供 Chat Completions 兼容入口，可作为后续混元接入路径；本轮尚无密钥，不能展示“混元真实调用成功”。[腾讯云：语言模型调用概览](https://cloud.tencent.com/document/product/1823/130079)

## 7. 北极星指标与边界

生产北极星指标：**在约定 SLA 内，完成核验且有结果记录的有效异常闭环率**。

`有效异常闭环率 = 期间符合条件的异常中，同时满足金额复核通过、证据充分、权限正确、责任人处理结果已确认的数量 ÷ 期间符合条件的异常总量`

演示不能测量生产闭环率，只能测量“可核验处理材料准备率”：异常说明、证据和人工下一步是否齐全。用户点击生成工单不算解决问题，回答字数和对话轮数不作为成功指标。

护栏：金额计算错误为 0；越商户数据泄露为 0；未经授权资金动作数为 0。其余指标包括异常识别 Precision / Recall、来源支撑率、有效拒答率、材料准备时长、人工修订率、每次有效准备成本。定义与上线阈值见 PRD。

## 8. 商业收益：只提供可检验假设

**示例参数全部是假设，不是已取得的经营成果。**假设每月处理 1,200 个异常，人工平均每个 8 分钟，辅助后的总人工时间为 5 分钟（包含复核），人工成本 60 元 / 小时；基础运行 800 元 / 月、模型 200 元 / 月、持续质检 400 元 / 月。

- 节省工时：`1,200 × (8 − 5) ÷ 60 = 60 小时 / 月`。
- 可节省劳动成本：`60 × 60 = 3,600 元 / 月`。只有当释放的工时可被重新利用，才是有效收益。
- 增量总成本：`800 + 200 + 400 = 1,400 元 / 月`。
- 月净收益：`3,600 − 1,400 = 2,200 元`；净收益 / 增量成本约为 `157%`。
- 盈亏平衡异常量：`1,400 ÷ [(8 − 5) ÷ 60 × 60] ≈ 467 个 / 月`。

若每单只节省 1 分钟，则每月收益 1,200 元，净收益为负 200 元；若只处理 300 个异常，即使节省 3 分钟也无法覆盖上述成本。因此应先验证频次与人工时间，不能以“AI 能提效”直接证明值得商业化。获客、销售、接入改造、历史数据治理和一次性研发成本尚未计入，需要在商业立项时补齐。

## 9. 为什么不选其他方向

| 方向             | 不作为首版的原因                                     | 对本项目的启示                                     |
| ---------------- | ---------------------------------------------------- | -------------------------------------------------- |
| 通用客服机器人   | 需求面过大，支付正确性与闭环责任不突出，难证明差异化 | 聚焦有结构化证据的异常，而非覆盖所有咨询           |
| 理财推荐         | 用户适当性、风险承受能力、产品资格与合规约束复杂     | 金融背景优先用于账务分析，不以推荐收益作为作品价值 |
| 泛营销聊天机器人 | 内容生成容易展示，却较难在无真实流量时验证转化归因   | 选择能离线复验的金额、证据和拒答能力               |
| 全自动退款 Agent | 直接操作资金，授权、幂等、审批和赔付责任更重         | 先做准备材料和辅助判断，将资金动作排除出首版       |

## 10. 验证与推进顺序

先复验合成场景；再访谈财务、店长、服务商支持人员并观察脱敏工作流；之后用历史账单影子运行。只有金额、隔离和未授权动作硬门全部通过，才考虑小范围辅助试点。真实模型必须单独做评测，不能将默认规则引擎的通过率算作混元表现。上线策略、回滚条件与剩余工作见 PRD 与技术设计。

作品提交价值在于：一套能点、能算、能解释、能复验的产品设计；而不是宣称虚构的腾讯实习、客户访谈、用户增长或线上收益。
