# 商证 MerchantLens｜演示与面试准备

## 1. 先把个人贡献讲准确

本作品源于候选人面向腾讯 AI 产品经理求职的完整项目需求。方案、代码与文档借助 AI 辅助生成和迭代。候选人目前没有完成商户访谈、真实模型调用、真实业务试点或线上收益验证，也不应声称逐行独立手写代码。

面试前需要亲自完成：运行产品、手算至少两组账单、阅读官方退款与账单规则、重跑评测、修改一个规则并观察影响、解释模型回退和上线门槛。完成后才可将“我复验了”“我修改了”作为个人贡献；未完成时用“方案设计为”“下一步计划验证”。

## 2. 两分钟项目介绍

以下是**熟悉并复验后**可采用的结构，请根据实际做过的动作调整：

“我围绕微信支付商户的对账和异常处理，制作了商证 MerchantLens 这个 AI 产品作品集。选择该场景，是因为我的金融工程和数据分析背景可以帮助我理解金额口径，而 AI 产品能力需要进一步体现在工作流、风险和评测上。

这个原型从 POS 与支付账单核对开始，定位重复、缺单、金额和退款状态等异常，再结合公开官方规则给出解释和人工工单材料。金额由整数分程序计算，模型只做语言层；涉及真实资金的动作不进入模型工具。

我希望展示的不只是聊天界面，而是范围、证据、计算、人工责任和评测的一整条链。静态演示已于 2026-10-04 通过 GitHub Pages 发布，使用合成数据与本地证据模式，另有 TokenHub / 混元接入代码；真实密钥调用和用户访谈还没完成。收益也只给了透明假设和盈亏平衡公式。

项目由 AI 辅助实现。我的个人贡献应以已经完成的需求判断、材料核验、运行复验和修改记录为准。我接下来重点验证财务实际处理时间，以及这种材料是否减少反复沟通，而不是用回答速度代替业务效果。”

## 3. 五分钟演示路线

| 时间      | 操作                           | 希望评审看到什么                                     |
| --------- | ------------------------------ | ---------------------------------------------------- |
| 0:00–0:40 | 选择商户 / 日期，解释金额口径  | 产品知道自己在核对什么；没有混淆交易、账面净额与到账 |
| 0:40–1:40 | 打开一条重复 / 缺单 / 金额异常 | 结论能够定位订单与记录，而非泛泛解释                 |
| 1:40–2:30 | 问“为什么不一致，下一步怎么办” | 计算证据与官方规则分别承担什么作用                   |
| 2:30–3:15 | 查看退款处理中案例             | 不把 PROCESSING 说成成功，也不承诺余额尚未扣         |
| 3:15–4:00 | 请求跨商户查看或直接退款       | 产品拒绝越界与越权，仍给允许的处理路径               |
| 4:00–4:35 | 检查工单草稿                   | 人工接续材料完整，生成不等于已执行                   |
| 4:35–5:00 | 查看实际评测 / 文档            | 能说清验收标准、局限与下一步                         |

不要以“高管都会认可”作为产品依据。评审看的是问题是否值得做、选择是否有逻辑、系统是否可复验，以及你是否诚实掌握了边界。

## 4. 高频追问与回答路径

### 为什么不是简单规则系统，为什么还需要 AI？

先承认金额和固定状态判断适合规则。AI 的增量价值应在自然语言理解、将多条证据组织成角色适合的说明、提出澄清问题和工单措辞上。当前没有真实模型效果证据，因此保留无模型的基线；用相同异常样本比较材料可用性、总人工时长和增量成本。模型没有显著收益就不用模型。

### 为什么选微信支付，和腾讯有什么关系？

它同时包含明确支付运营规则和大量实际工作流的可能性，与金融科技相关岗位方向吻合。微信支付是业务规则来源，混元 / TokenHub 是可选语言能力，企业微信是待验证协作入口。没有必要把游戏、广告、内容等所有业务都塞进首版。是否适合真实腾讯产品线仍需岗位与用户需求验证。

### 你怎么确定商户真的需要？

目前只是基于公开规则与自身背景的痛点假设。下一步先观察财务如何完成一笔差额核查，再访谈不同角色，收集脱敏异常结构、现有处理时长、反复沟通次数和最终责任人。不先问“你想要 AI 吗”，而是问“最近一次对不上的订单怎么处理、最耗时间在哪里、错误的代价是什么”。

### 你最重要的产品取舍是什么？

首版选择“准备可核查材料”，放弃“自动退款”。前者能用合成数据与公开规则复验，后者需要真实授权、审批、幂等、风控和责任机制。模型灵活性也让位于确定性金额和范围，遇到信息不足不硬答。

### 用 RAG 能保证不幻觉吗？

不能。检索可能召回错片段，来源可能过期，模型也可能错误解释。必须同时检查来源适用性、结论是否被支撑、数字和状态是否一致。当前是小规则库的词项检索，不是向量检索；上线还要准备语义改写、无答案、冲突规则与注入攻击样例。

### 商户下拉选择能保证租户安全吗？

不能。演示中它只限定合成数据范围。生产需要服务端身份与商户授权映射，数据读取按权限控制，不能信任前端参数。还要做跨租户对抗测试与审计。作品不能将演示过滤声称为已完成企业级鉴权。

### 金额差额是商户损失吗？

不是。它只是两侧指定范围记录的差。要核对订单缺失、重复、账期、退款日期等原因。账面净额也不是银行到账或利润；在没有资金账单和银行流水时，不应下“钱少了”的结论。

### 退款处理中为什么不扣成功退款？钱没扣吗？

这里的净额只统计已完成的退款结果。PROCESSING 不表示资金没有变动；官方流程中，退款受理后资金可能先进入退款中间账户。要区分状态确认与资金流。产品应说明这种口径局限，不给出实际余额承诺。

### 你如何衡量成功？

生产以核验后有处理结果的异常闭环为目标；演示只能验证材料准备。金额、权限和未授权资金动作是硬门。再看识别精确率 / 召回率、引用支撑率、人工修订和总人工时间。不能用满意度一个分数掩盖金额错误，也不能把点击生成工单算解决异常。

### 你的 ROI 从哪里来？

示例参数是可替换假设。收益来自异常量 × 每单节省的含复核人工时间 × 人工成本，减运行、模型与质检成本。若异常量不足，或 AI 解释增加复核时间，ROI 会为负。真实试点需计时并评估被释放时间能否转化为工作收益；示例还未包含获客、接入与一次性研发费用。

### 测试通过是不是可以上线？

不是。合成场景结果只能证明这些输入下的实现行为。真实模型、真实数据、身份权限和业务协作需单独验证。先做影子运行，再小范围材料辅助；任何金额或跨租户失败都停止扩容并回滚。

### 你的个人贡献，哪些是 AI 做的？

按事实说明：我提出求职用途、腾讯 AI 产品方向和完整可演示的要求；AI 辅助完成方案与代码。之后我本人做了什么，要展示运行、核算、修改和学习记录。如果还没有做，明确说正在补足，不将 AI 输出冒充独立研发经验。能够解释和改进作品比背诵一个虚构主导故事更有说服力。

## 5. 手算练习

从界面任选一个商户 / 日期，抄下导入成功支付金额、手续费和 SUCCESS 退款，手算账面净额；再算 POS 总额 − 支付交易总额。注意首版 POS 总额保留导入的重复记录，不是去重后销售额。找到一条异常，确认涉及订单与原始证据。解释为什么它是“待核查”而非已确定损失。

然后更换商户与日期，证明旧范围订单不进入新答案。用非支持日期提问，观察是否澄清；用跨商户或退款执行要求提问，观察是否拒绝。最后打开评测报告，讲清一个通过场景和一个测试局限。

## 6. 提交前清单

- 亲自跑完完整演示，能在无模型密钥的情况下说明默认模式。
- 阅读官方账单与退款规则；能说明手续费只是演示合同费率。
- 保存自己的复验与修改记录，明确 AI 辅助范围。
- 在实际报告生成后填写真实测试分母与结果，避免预填“全部通过”。
- 使用 [已发布的在线入口](https://harry-bytefina.github.io/merchantlens/) 复验演示与移动端；首个发布结果见 [Actions 记录](https://github.com/harry-bytefina/merchantlens/actions/runs/37142662688)。当前访问检查仅覆盖本设备及无需身份认证的 HTTP 请求，中国大陆网络与不同设备尚未验证。
- 获得密钥后单独运行模型评测；不能将规则引擎结果标为混元成绩。
- 申请材料只写已完成事实，未完成项以计划表述。
